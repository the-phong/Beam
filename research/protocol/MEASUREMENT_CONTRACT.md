# S02 measurement contract — proposed definitions and decision timing

Status: S02 design candidate for independent review. This document fixes **what** is counted, **where** it is observed, and **when** a feature is available. It does not claim the telemetry exists; S05 implements and validates it, S06 freezes calibrated numerical loads and collector settings, and S07 proves end-to-end reproduction. A missing stream is `NOT MEASURED`/`null`, never a fabricated zero. The final S02 contract must be frozen before confirmatory File 02 runs.

S05 implementation status (2026-11-10): the
[metric dictionary](METRICS_DICTIONARY.md) maps this contract to observed
application, controlled RPC, native Comet mempool/P2P and Linux process
signals. Exact Comet CheckTx queue wait and P2P transaction ingress remain
`NOT MEASURED`; therefore S05's full gate and loaded RQ1–RQ3 runs remain
closed. Historical S02 design wording below is retained for provenance.

## Run identity, controls and valid comparisons

Each run records `run_id`, immutable source/tree and protocol version, profile, genesis/config hash, four-validator host topology, CPU model/features and limits, OS/toolchain/Comet/crypto versions, mempool/consensus limits, RPC/P2P source, corpus and seed, planned/actual offered tx/s and bytes/s, warm-up/steady/drain times, time-sync error bound, collector version, raw SHA-256, oracle result and QC status. A fresh network or a separately proven reset is required. Raw results are append-only; reruns receive new IDs. Historical Phase 05 runs never enter this dataset.

The only intended experimental factors are authentication profile C/CP/P/H, workload class/capability, traffic regime, offered rate and controlled ingress source. Across a paired comparison hold the logical transfer stream, genesis accounts/balances, account/nonce schedule, consensus and mempool configuration, block interval, hardware/placement, collector mode, warm-up/drain and seed fixed. Randomize or counterbalance order to control drift. For a **constant-rate** segment, a rate is achieved only if its steady-state total is within ±5% of plan and each non-overlapping decision window with planned sends reaches at least 90% of its planned count. For a burst or planned-zero segment, compare the actual per-window send count and onset/offset with its frozen schedule; S06 must preregister tolerances for those segments before confirmatory runs. A failure is `RATE_MISS` and excludes the affected pair. The generator reports planned sends separately from actual sends; it cannot silently throttle a profile to make a comparison look successful.

Run three traffic regimes separately: `equal_tx_s`, `equal_bytes_s` and `fixed_legitimate_plus_adversarial`. A fourth `matched_pressure` comparison declares exactly one matched variable (tx/s, bytes/s or observed accepted occupancy) and lists all unmatched variables. For the first two, derive profile schedules from *actual canonical wire sizes* verified in S03; exact byte matching is mandatory for CP versus H. Under attack, keep the legitimate offered stream constant and add adversarial traffic, then compare with a separate benign high-load control at the declared pressure. No B0/B1 raw delta is used as a crypto causal contrast.

## Event and clock contract

| Symbol | Event and authoritative source | Availability rule |
|---|---|---|
| `t_plan` / `t_send` | Generator planned deadline / actual socket send of one unique tx | Generator monotonic clock; these are distinct fields. |
| `t_ingress` | Validator receives full RPC payload or controlled P2P envelope | Validator monotonic clock; capture before precheck if instrumented. |
| `t_precheck_done` | Comet full/size/precheck/cache decision | Available only after that decision; a cache hit has no Pluto crypto span. |
| `t_checktx_start`, `t_checktx_done` | Application CheckTx service entry/return, excluding prior queue wait | Validator monotonic clock; code and stage become available at return. |
| `t_mempool_add` / `t_recheck` | Comet accepted-list insertion / later post-Commit recheck | Count only actual accepted entries; a CheckTx rejection is never occupancy. |
| `t_peer_tx`, `t_peer_rx` | Actual mempool P2P send/receipt at peers | Do not infer from RPC or consensus block gossip. |
| `t_proposal`, `t_commit` | Proposal processing / block committed and observable at validator | The oracle independently matches block height, AppHash, tx ID and account state. |
| `t_feature_available` | Collector has the complete, valid feature window and timestamp | At least window end plus ingestion delay; no feature may be backdated to event time. |
| `t_alert` | Detector emits a decision using only available windows | Use collector decision timestamp, including processing and delivery delay. |

Use monotonic clocks for durations within a process and UTC wall time only for correlation. For cross-host latency and alert lead time, S06 must measure clock offset and uncertainty around every run (or use a round-trip bounded mapping). If the uncertainty interval overlaps zero lead time, report `LEAD_TIME_UNRESOLVED`; do not claim an early alert. Lost or out-of-order telemetry increments a drop counter. A missing capture point remains `NOT MEASURED` until S05 implements it. CometBFT distinguishes `broadcast_tx_sync` admission from block inclusion; RPC return latency is not inclusion latency. [Pinned CometBFT transaction guide](https://github.com/cometbft/cometbft/blob/v0.38.26/docs/core/using-cometbft.md).

## Metric dictionary

| Metric | Unit and computation | Observation point / first availability | Required caveat |
|---|---|---|---|
| Offered legitimate/adversarial tx and bytes | Actual distinct sends and sum of encoded wire lengths per second; planned values separately | Generator, at send | Not equal to CheckTx requests or accepted tx. |
| Ingress RPC/P2P tx and bytes | Count and payload bytes by source per window | Validator ingress, after full payload arrival | P2P must have a real controlled peer path. |
| Precheck/cache reject by reason | Count by full, size, precheck, app connection, duplicate/cache | Comet precheck response | Not Pluto crypto time and not accepted mempool occupancy. |
| CheckTx queue wait / service | Monotonic ns from Comet enqueue→application entry / application entry→response | Validator, when response completes | Distinguish client round trip and recheck from first admission. |
| Structural, binding, secp, ML and state spans | Monotonic ns and reached-stage counter for each attempted stage | Application stage exit | A zero duration is valid only when stage was reached; otherwise `null`. Stage instrumentation overhead measured ON/OFF in S05. |
| Accepted mempool count / bytes | Instantaneous accepted list entries and sum of their encoded lengths | Comet list insertion/removal/recheck; sampled with timestamp | Never add rejected or duplicate traffic. Report both count and bytes. |
| Relay ingress/egress bytes and propagation | Mempool-channel payload bytes per peer and bounded send→peer receive duration | Actual P2P instrumentation | If absent, `NOT MEASURED`; block gossip is separate. |
| Process CPU / RSS | Delta user+system CPU seconds per wall second (core-equivalents), peak resident bytes for validator/Comet and collector processes separately | Host process sampler after window | Process CPU is not “PQC CPU”; stage spans and profiler support attribution. |
| Legitimate goodput | Distinct legitimate tx committed on all four validators at a common height per steady-state second | Independent block/state oracle after commit | Exclude rejected, replayed or duplicate tx; report offered rate and drain completion. |
| Legitimate inclusion latency | `t_commit_observed - t_send` for a unique legitimate tx; p50/p95/p99 with n and censoring | Only after independent commit observation | Never assign latency to rejected or uncommitted tx. RPC sync latency is separate. |
| Validator agreement | Same-height block ID/AppHash, balances, nonces and total supply across four nodes | Oracle after a common height | Divergence is a hard QC failure, not a performance sample. |
| Detector quality and cost | TP/FP/TN/FN, recall at fixed FPR, FP/hour, lead time, inference p99, CPU/RSS | Held-out decision windows after feature availability | Report run-level confidence intervals and training/selection split. |

Within a run, per-transaction samples may describe a distribution but are **not independent replicates** for hypothesis CIs. Aggregate one outcome per independent run, then calculate paired effects and 95% CIs across runs. RQ2 recall uses independent attack runs as its denominator; benign windows within a run remain clustered for FPR inference. S06 must preregister a cluster-aware confidence procedure and demonstrate enough benign observation to support a one-sided 95% upper FPR bound of 1%; zero observed false alarms in a small sample cannot be treated as a zero upper bound. Report sample counts for p99 and do not report a percentile when its numerator/denominator is unavailable or censored beyond the preregistered limit. S06's precision pilot fixes the number of independent runs and decision-window length before File 02. Exploratory plots are labeled separately.

## Experimental degradation and early alert

S06 collects disjoint **benign-only calibration runs** for each profile, offered-rate stratum and topology. From non-overlapping decision windows it freezes `G_min` as the 1st percentile of benign committed-legitimate-goodput/offered-legitimate-rate and `L_max` as the 99th percentile of benign p95 inclusion latency of transactions **completed in that window**. These are study-specific experimental service bounds, not production SLOs. If calibration sample size cannot estimate either bound reliably, RQ2 cannot claim early detection for that stratum.

An attack run has a degradation event only if the **same** bound is breached in three consecutive windows. The offline oracle assigns `t_degrade` to the end of the *first* window in that sustained sequence; it may inspect later windows solely to confirm ground truth. The detector never receives this future confirmation. An eligible early true alert must satisfy `t_attack_actual_send <= t_alert < t_degrade`, after subtracting the cross-host timing uncertainty. A pre-onset alert is a false alarm. A run without a confirmed degradation event contributes **zero** successful early warnings to the preregistered RQ2 run-level recall denominator; attack recognition on such a run is reported separately. Alert lead time is `t_degrade - t_alert`, with its uncertainty interval. Do not call an alert early merely because it precedes the end of the run.

The detector feature sets are frozen before holdout: `F1` ingress rate/bytes and source; `F2` adds completed precheck and verification-stage counts/durations **only after their completion**; `F3` adds accepted mempool and directly observed P2P relay. A detector never sees `case_id`, scenario label, future block outcome, current test split, seed, wall-clock run schedule, raw key/account identity or a rejection code before CheckTx returns. Train and tune on complete runs disjoint by network/seed from the final test runs; select the candidate detector and simple-baseline threshold using validation only. The same feature availability, decision cadence, calibration data and held-out runs apply to threshold, EWMA, CUSUM, fixed rules and ML. If F3 P2P is unmeasured, compare only F1/F2 and report F3 unavailable.

The study FPR target is ≤ 1% of non-overlapping benign decision windows, with the **upper** run-level 95% confidence bound required to meet the target on held-out data. Also report false alerts/hour with observation hours and CI. The primary RQ2 class is late bad ML proof after valid secp in H; other classes are secondary. RQ3 claims require ML recall improvement over the strongest validation-selected simple baseline at the same FPR, no worse median lead time, and collector-side p99 inference ≤ 10% of window length, mean CPU ≤ 0.25 core, peak RSS ≤ 512 MiB. A smaller benchmark training set, outcome-selected threshold or window overlap cannot be used to inflate apparent detector performance.

## Quality control, exclusion and safety stop

Before analysis, the oracle checks every run's source/config/seed identity, corpus feasibility, profile equivalence, valid/invalid expected codes and reached stages, unique tx count, common-height state agreement, generator achieved rate, clock continuity, sampler drops, collector ON/OFF decision invariance and raw file hashes. Failed runs remain immutable with `INVALID_FOR_ANALYSIS` and a reason; a replacement run has a new ID. The exclusion rule is fixed before outcomes are seen. If the generator, network or observer cannot meet the planned regime, report `NOT FEASIBLE WITHIN SAFE RANGE` rather than lower the offered load for one profile.

No high-load run may start without S06 supplying explicit lower-of-configured-and-hard caps for tx/s, bytes/s, generator queue, validator CPU/RSS, free disk, duration and endpoint allowlist; unset/zero caps cause preflight refusal. Hard ceilings per run: **10 minutes**, **90% of a VM's allocated CPU for 30 continuous seconds**, **80% of its allocated RAM**, or **<10% free disk**; S06 may lower these after pilot. Abort immediately on AppHash/state divergence, two unavailable validators, traffic outside the private allowlist, collector failure that obscures safety metrics, or a manual kill switch. Drain and preserve a failed run's raw evidence privately; no automated retry on the same run ID. These are experiment guardrails, not DoS thresholds. The generator/collector must be separate from validator processes. Four VMs on one physical host remain a shared-fault-domain pilot, and multi-host relay claims require independently controlled hosts and measured clocks/network.
