# S06 isolated testbed and offered-load contract

## Scope and pinned configuration

S06 uses four real CometBFT v0.38.26 validator processes on **one WSL2 Ubuntu host**. This is a controlled pilot, not four independent VMs or an infrastructure-fault experiment. Each validator has its own temporary home, validator/node key, localhost P2P/RPC/ABCI ports, app store and telemetry observer. The app servers run in the integration harness process; the load generator and each of the four collectors are separate OS processes. The harness binds every listener to `127.0.0.1`. Fresh temporary homes are destroyed after each run; private keys and unsanitized logs never enter Git.

The executable configuration is [`../config/s06_pilot.json`](../config/s06_pilot.json). The test applies its values to CometBFT: `flood` mempool, size 128, maximum mempool bytes 8 MiB, cache 1024, maximum transaction 8192 bytes, recheck and broadcast enabled; maximum block bytes 1 MiB; empty blocks every 1 s and commit timeout 1 s. It uses the source-checked S05 Comet overlay built from the pinned module, solely to observe P2P transaction ingress and CheckTx socket queue measurements. CometBFT consensus is not changed. The config hash, genesis hash and plan hash bind each run.

## Generator and workload plans

`cmd/profile-load` reads a private, pre-signed plan and submits each unique transaction using an absolute monotonic deadline. `planned_utc` is the target and `actual_send_utc` is the HTTP `WroteRequest` callback after the request was written to the socket; the plan queue time and RPC completion are separate fields. A full bounded submission queue fails the run. The generator never signs, reuses a wire hash or silently slows the plan. The fixture allocates a separate funded sender with nonce zero per legitimate transaction, so concurrent scheduling does not create artificial nonce conflicts. Each run starts from a fresh identical genesis for its profile. The private plan contains account slots and scenario labels; only public example vectors live in Git.

The offered source is **RPC** (`broadcast_tx_sync`), restricted to an exact `127.0.0.1` origin with no proxy or redirects. CometBFT's subsequent transaction relay is separately counted as **P2P ingress** by the S05 observer. This pilot makes no claim that transactions were injected through the P2P wire. A plan declaring P2P source is rejected until a genuine P2P sender exists.

Three regimes are explicit: `equal_tx_s` matches target transaction count per second, `equal_bytes_s` matches serialized bytes per second, and `fixed_legitimate_plus_adversarial` holds the legitimate stream while adding invalid traffic. Constant regimes validate a target within ±5% across the steady interval before a run. During a run, actual socket writes must reach at least 95% of the steady target and 90% of every one-second nonoverlapping planned window. Fixed streams are checked separately. Misses are recorded as `RATE_MISS` and excluded from comparisons. The pilot also covers a burst waveform: every planned burst window must have 90–110% of its planned sends, and planned-zero steady windows must have zero sends; the one-second window boundary is the onset/offset tolerance. This is offered load, not accepted throughput or committed throughput.

The public [`../corpus/s06_scenarios.json`](../corpus/s06_scenarios.json) records benign low, benign high, burst, valid high, malformed early, invalid secp256k1, invalid ML-DSA-44 after valid secp256k1, and signed but state-invalid vectors. Its generator/verifier checks expected code and stage with the direct oracle. Capability labels distinguish arbitrary malformed bytes from possession of a signing key and both keys. The late invalid vector is a correctly signed transfer from an insufficiently funded account. The pilot does not equate an early malformed vector with a cryptographic attack requiring private keys.

## Run order and safety

The integration pilot shuffles seven named jobs with recorded seed 611. Each plan uses a 1 s warm-up, 4 s steady interval and 3 s drain. The hard limits are 25 tx/s, 65536 serialized bytes/s, 16 outstanding requests, 60 s wall time and 2 s RPC request timeout. Every observer samples once per second. The generator refuses to start without four distinct live validator/observer identities, current samples, enough free disk and safe memory. It checks the `STOP` file, same-height AppHash agreement, validator availability, collector health, process identity, watched CPU, watched RSS, host memory and disk during the run. A safety failure cancels outstanding HTTP requests and marks `SAFETY_ABORT`. Sustained CPU >=90% for 30 s, RSS or host memory >=80%, disk free <10%, two unavailable validators, observer loss/staleness or a manual kill file stop the run. The output remains a private local artifact. The test also asserts post-run four-validator account state and separate P2P relay observation.

Reproduce the bounded pilot with `make test-s06-pilot`. It is deliberately small; it does not establish a DoS result, network independence, saturation capacity or RQ1–RQ3 effect estimate. See [`../evidence/s06/TESTBED_REPORT.md`](../evidence/s06/TESTBED_REPORT.md) for exact local verification and limits.

The separate S02 scientific contract's benign calibration and false-alarm precision requirements remain open. A conservative zero-false-alarm design would need at least 299 *independent* benign decision observations to put the one-sided exact binomial 95% upper bound below 1%; overlapping windows from these seven runs do not count as independent observations. Clustered multi-window analysis needs a preregistered run-level procedure and more independent runs. No `G_min`, `L_max`, precision estimate or early-warning claim is frozen by this pilot. These are explicit gates before confirmatory File 02 analysis, not outcomes inferred from the S06 technical gate.
