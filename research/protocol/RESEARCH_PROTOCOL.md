# S02 research protocol — proposed contract for independent review

Status: S02 design candidate, 2026-11-09. The source baseline is `test-mainet` commit `0bdd869f2c6b3ed59b0ae825954d8667b3c7481e`; S01 implementation checkpoint is `484c64788883a482c0e8fdba49f80a0e2126617b` (Draft PR #12). This document defines the new RQ1–RQ3 study. It does not import Phase 05 results, authorize a load run, or assert that any of the four experimental profiles exists. S03–S07 and File 02 must satisfy their own gates.

## Research questions and falsifiable decisions

The experimental unit for inference is an **independent network run**, not an individual transaction, packet, sample or overlapping time window. A run has a fresh chain/home, source revision, configuration hash, host topology, offered-load plan, seed and immutable ID. Pair runs by intent stream, seed, workload regime and host; randomize or counterbalance profile order. Any proposed effect must be reported with its estimate, run-level 95% confidence interval, number of independent runs and achieved load. A failed validity oracle or missing measurement makes the contrast unavailable, not zero.

| Question | Confirmatory contrast and primary outcome | H0 / H1 | Decision and falsification |
|---|---|---|---|
| **RQ1 Resource Impact** | H minus CP on per-run mean **application CheckTx service time for valid, accepted transfers** at the same offered tx/s and exact wire bytes per matched intent. Queue wait is measured separately. C versus CP estimates size/transport effects; P and other regimes are secondary. | H0: the H–CP service-time difference is ≤ 0. H1: it is > 0. | Reject H0 only if the run-level 95% CI lower bound is > 0 and all profile equivalence, rate and oracle checks pass. A CI upper bound ≤ 0 falsifies the proposed positive effect under tested conditions; a crossing CI is inconclusive. Even a positive result is **resource cost**, not a DoS finding. CPU, legitimate goodput, latency, accepted mempool and relay are required secondary outcomes, never silently substituted for the primary one. |
| **RQ2 Detectability** | Within H, late ML-invalid traffic that passes structural, binding and secp checks versus matched benign high-load traffic. Primary outcome: share of **all preregistered attack runs** with a detector alert before experimental degradation, at a validation-calibrated false-positive rate ≤ 1% of non-overlapping decision windows. An attack run without measured degradation counts as no successful early warning. | H0: pre-degradation recall is ≤ 80% at the FPR target. H1: at least one time-available detector exceeds 80% on held-out independent runs while meeting the FPR target. | Reject H0 only when the run-level lower 95% CI for pre-degradation recall is > 80%, the held-out benign FPR upper 95% CI is ≤ 1%, and alert time precedes degradation with clock uncertainty accounted for. A CI upper bound ≤ 80% falsifies the proposed useful detectability under tested conditions; a crossing CI is inconclusive. Other attack families are reported separately and do not rescue a failed primary class. |
| **RQ3 Baseline Gap** | Best eligible cost-aware ML detector versus the strongest of threshold, EWMA/CUSUM and fixed rules on identical held-out runs, features, decision times and FPR ≤ 1%. Primary outcome: difference in pre-degradation recall. | H0: ML does not improve recall over the strongest simple baseline under equal FPR and cost limits. H1: ML improves recall and meets those limits. | Reject H0 only if the run-level 95% CI lower bound for ML minus the strongest baseline is > 0, held-out FPR upper bounds are ≤ 1% for both, ML median lead time is not lower, and its p99 inference time ≤ 10% of the decision window, mean detector CPU ≤ 0.25 core and peak RSS ≤ 512 MiB on the dedicated collector. If ML fails any required condition, do not claim an ML advantage. A CI upper bound ≤ 0 falsifies a positive recall gap under tested conditions; otherwise inconclusive. |

The 80% recall, 1% FPR and detector cost limits are **study design choices for review**, not a production alarm policy or universal scientific threshold. Also report false alerts per hour and the uncertainty of that estimate; insufficient benign observation makes RQ2/RQ3 inconclusive. The numerical offered rates, window length and required run count are selected from a separate S06 precision/safety pilot and frozen **before** confirmatory File 02 data. The selection algorithm, split boundaries, seed list and exclusions must be preregistered; no outcome-dependent rate or threshold changes are permitted.

## Four controlled authentication profiles

All four profiles use one new experimental application and the same logical one-unit transfer: chain ID, sender account, recipient account, positive amount, exact next nonce and conserved total supply. They share the same canonical account registry, genesis balances, receiver policy, state transition, persistence layout, AppHash rule, ABCI++ callbacks, CometBFT version, mempool and consensus configuration. One genesis registers **both** a secp256k1 and an ML-DSA-44 public key for every fixed account; keys are **genesis-only**, never placed on the transaction wire. An account ID is a fixed registry key independent of the authentication profile. Each profile authenticates the same canonical logical intent with a profile-separated domain so signatures cannot be replayed across profiles. The envelope and canonical signature/padding rules are specified and tested in S03; no accepted B0/B1 wire or state rule changes.

| Profile | Authentication condition | Wire-size role | Interpretation |
|---|---|---|---|
| **C** | Registered secp256k1 signature valid | Classical reference | Baseline for C→CP byte-cost contrast. |
| **CP** | Same secp256k1 condition, plus a single canonical all-zero padding field accepted as valid transaction content | **Exactly byte-matched to H** for the same intent; padding length derives from the complete H envelope length and is fixed by the canonical codec | C→CP isolates the byte/parse/hash consequences of a larger accepted transaction without ML verification. It must commit the same transfer. |
| **P** | Registered ML-DSA-44 signature valid | ML-only length is measured, not assumed equal to C or H | An alternative algorithm profile; its raw C/P difference is not claimed to isolate crypto from size. |
| **H** | Registered secp256k1 **and** ML-DSA-44 signatures valid over the same canonical intent | Reference length for CP | CP→H examines incremental hybrid verification and profile-specific parsing at equal wire size. The stage breakdown is required before attributing any difference specifically to ML verification. |

The CP padding is a fixed all-zero field in the canonical wire envelope, with one permitted length/encoding; it is structurally checked but excluded from the secp signed-intent digest. H's ML proof bytes are likewise excluded from its secp signed-intent digest, so neither secp verification hashes its size-control field. The profile-separated digest still authenticates the logical transfer and cannot authorize a different profile. Nonzero or wrong-length CP padding is malformed, while canonical padding is a valid accepted transaction. S03 must test these properties and account for any remaining parser/structural-check cost in the stage breakdown. If exact matching cannot be achieved within the configured Comet transaction cap, profile equivalence fails and no RQ1 contrast is run. H and P retain the final FIPS 204 ML-DSA-44 parameter set; the standard lists 1,312-byte public keys and 2,420-byte signatures. [NIST FIPS 204](https://nvlpubs.nist.gov/nistpubs/fips/nist.fips.204.pdf). The chosen genesis-only key policy limits external validity to preregistered accounts; on-wire-key costs are outside this primary experiment and must be a separately labeled sensitivity study if later needed.

## Comparisons, load and interpretation

1. Run **equal tx/s** and **equal bytes/s** regimes separately. H and CP exact size matching makes these equivalent for a matched stream, but C and P require separate schedules. Record planned and actually achieved rates; a missed target invalidates that contrast rather than silently changing load.
2. For attack mixtures, keep the legitimate offered stream fixed and **add** an adversarial stream. A separate benign high-load control must match the chosen pressure variable (tx/s, bytes/s or accepted occupancy). State explicitly which variables cannot be matched simultaneously.
3. Use profile-specific valid-only baselines at the same topology/rate. Treat B0/B1 Phase 05 results as historical context only: their wire, registry, state and persistence differences are confounders, as documented in `../evidence/s01/LEGACY_INVENTORY.md`.
4. Distinguish three mechanisms defined in `THREAT_MODEL.md`: rejected verification work before accepted mempool entry, accepted mempool byte/count pressure, and actual P2P relay congestion. A high rejection count alone establishes none of them.
5. Run correctness oracle and achieved-rate QC before resource analysis. A positive CheckTx cost does not imply a network bottleneck; a network/relay claim requires directly measured P2P and a controlled topology. No attack or DoS claim is made without measured legitimate service degradation relative to matched benign controls and a recorded saturation point within safety caps.

## Gate order

S02 is a document and review gate. S03 must implement and test the profiles and equivalence; S04 must establish BFT correctness; S05 must instrument the measurement points; S06 must freeze topology, rates, safety limits and sampling from a pilot; S07 must prove end-to-end reproducibility. Only File 02 may execute confirmatory RQ1–RQ3 experiments, and RQ2/RQ3 claims depend on the preceding quality gates. The independent Controller/Owner review required by `AGENTS.md` is separate from this author's completeness check.
